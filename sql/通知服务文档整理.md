## 一、Notification Plan – 2025.11（Confluence 页面）

页面路径：API One Stop Architecture Design。创建者 Austin Chen，最后由 Ying Ying Gou 于 2026 年 10 月 21 日更新，阅读约 5 分钟，232 次浏览。

### 背景：这个通知服务的使用场景是什么？

- **流程通知消息（Process Notification Message）**：与业务逻辑消息无关。
- **监控消息（Monitoring message）**：告知监控中心或其他系统当前请求的状态。该消息丢失不会影响用户的业务服务，只会影响监控服务。
- **告警消息（Alert Message）**：客户端和我们的 emergency alerts subscriber 起初会同时发送给 xMatter，xMatter 会丢弃重复的告警。
- **用户消息（User message）**：系统或用户需要通过 staff id 向特定用户发送消息，例如"用户的请求已被批准"的通知。

### 哪些消息不应该走这个服务？

- 与业务逻辑相关的消息。例如系统完成步骤 A 后需要通知下游客户端处理步骤 B，这类消息不允许走本系统。
- 需要实时响应的请求。例如需要获取外汇汇率或股票价格。

### 功能列表（Feature List）

1. 重构 Sonic 代码。
2. 向客户端提供消息发布 API 契约，由客户端发送告警。
3. emergency alerts subscriber 根据消息类型发送给 xMatter 或邮件。
4. 工具系统（tooling system）集成用户消息 subscriber，并在其工具用户页面展示用户消息。
5. 针对当前的流程监控作业，构建 UI 和服务。UI 展示该批处理或环境检查处于什么状态。服务提供 2 个功能：
   1. 在 DB 中新建一个硬编码的流程。
   2. 使用 process subscriber 修改该流程的状态。

## 二、架构图

**组件及流向：**

- **Client Systems**（3 个）→ **messagePubAPI** → 分发到两个 Kafka Topic：
  - **Kafka Alert Topic**
  - **Kafka Message Topic**
- **Kafka Alert Topic** 被三个订阅方消费：
  - **emergency Alerts sub**（紧急告警订阅者）
    - 向上发送到 **xMatter**。
    - 向左发送 **email**。
    - 连接数据库 **unacknowledgeMessageCache**（未确认消息缓存）。
    - email 对相关人员进行 repeat Notify（重复通知）。
    - 人员通过 **Acknowledge API** 向 xMatter 确认（acknowledge）。
  - **Monitoring Center → Alerts sub**
  - **Process Center → state change message sub**（状态变更消息订阅）
- **Kafka Message Topic** → **User Center → message sub**

### messageLevel（Java 枚举）说明

| 级别 | 含义 | 处理方式 |
|---|---|---|
| OFF | 系统不可用，需要立即处理 | 1. 发送邮件和 xmatter |
| FATAL | 程序中出现严重情况，需要介入以防止系统故障 | 1. 发送邮件和 xmatter |
| ERROR | 出现影响部分操作的错误，但严重程度低于严重（critical）情况 | 1. 发送邮件 |
| WARN | 表示潜在问题，如果不处理，将来可能导致错误或意外行为 | 1. 发送邮件 |
| INFO | 记录系统正常运行的消息 | （空） |
| USER_MESSAGE | InApp 通知消息 | OFF、FATAL、ERROR 的消息也会发送到用户消息 topic |

## 四、receiver configuration 接收方配置

### 1. xmattersConfig

| 参数 | 是否必填 | 说明 | 最大长度 |
|---|---|---|---|
| aboutKey | 可选 | 此告警是关于什么的 | |
| aboutSource | 可选 | 此告警所涉及应用在告警时所处的位置，IP 地址 | 64 |
| key | 必填 | 发送方应用 ID，请联系开发团队获取该服务的访问权限 | |
| source | 可选 | 发送应用在告警时所处的位置，IP 地址，最多 64 个字符 | |
| type | 必填 | 固定文本 "ALERT" | |
| version | 必填 | 固定文本 "alertapi-0.1" | |
| object | 必填 | 告警所指向的应用内组件。可为任意文本，该字段对区分应用内不同组件很重要，最多 128 个字符 | 128 |
| occurtime | 可选 | 告警发生时间，整数 epoch 时间，单位为毫秒（ms）。Epoch 时间为 UTC。显然存在 2 种 epoch 时间规范。毫秒级 epoch 时间应类似 occurtime=1344690518000，可数位数确认 | |
| severity | 必填 | 基于事件管理的告警严重度矩阵（Alert Criticality Matrix），severity 用于定义告警行为，即**创建事故工单**和/或 **xMatters 通知** | |
| text (messageContent) | 必填 | 告警文本（注意 development tips 中不支持的字符） | 1024* |

**severity 对应矩阵：**

| 严重度 | 创建事故工单 | xMatters 通知 |
|---|---|---|
| CRITICAL | ✅ | ✅ |
| MAJOR | ❌ | ✅ |
| MINOR | ❌ | ✅ |
| WARNING | ❌ | 仅邮件 |
| INFO | ❌ | ❌ |

补充说明：

- 上述严重度映射基于 **RRE Monitoring and Alerting team** 提供的 Alert Criticality Matrix，请始终参考其 Confluence 页面了解详情。
- 注意：发送给 Alert API 的 severity 现在支持大写和非大写字母。Alert API 已增强，会在发送到上游事件管理基础设施之前将 severity 全部转为大写。
- 1024 个字符包含系统会添加到消息前面的前缀 "[Your application name] issued the following alert:"，之后才发送到事件管理系统。Alert API 有自动截断功能，会截断超过 1024 个字符的消息文本。

### 4. Headers（请求头）

| 名称 | 是否必填 | 说明 |
|---|---|---|
| X-HSBC-E2E-Trust-Token | 必填 | 包含已认证调用方（或主体）的身份信息。E2E trust token 只能由身份提供方（IdP）生成 |
| X-HSBC-Request-Correlation-Id | 必填 | 包含由发起请求的客户端应用（如下例中的 Web 应用）为每个请求生成的 UUID。它会通过该请求头在所有 API 层间级联传递，以帮助将原始请求与为满足该请求而发起的具体 API 调用关联起来 |
| traceparent | 可选 | traceparent HTTP 头由 W3C Trace Context 规范定义。它携带追踪上下文信息，包括 trace ID、span ID 和 trace flags，支持跨服务的分布式追踪。该头允许下游服务关联请求并保持分布式事务的完整追踪 |
